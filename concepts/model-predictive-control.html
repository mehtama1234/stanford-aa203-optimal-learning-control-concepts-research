Model Predictive Control

Repeatedly solve a finite-horizon control problem, apply the first action, observe the new state, and solve again.

01 · the ordinary pressure

Why this idea has to exist

A controller needs future planning but cannot perfectly trust a long open-loop plan.

The tempting shortcut is simple: Compute the whole plan once and execute it blindly. But that shortcut breaks because disturbances and model errors make the real state drift from the planned trajectory.

02 · the object

What the math keeps track of

The controller keeps track of a receding-horizon optimization problem. This answers a practical question: look for repeated short-horizon optimization in a feedback loop.

The operation is concrete: Optimize over a horizon, apply the first control, shift the horizon, and replan.

03 · one concrete run

Work it through before naming the formula

An autonomous car plans five seconds ahead, but only drives the first tenth of a second. Then it looks again. The old plan was not wrong; it was temporary. Traffic moved, the measured state changed, and the next optimization should start from the real state, not the predicted one.

the actual math, one level deeper

MPC repeatedly solves a finite-horizon problem, applies the first control, shifts the horizon, and solves again. Recursive feasibility asks whether that first control leaves tomorrow's problem solvable.

04 · boundary

Where the idea stops working

The optimizer must solve fast enough and the horizon/terminal conditions must protect future feasibility.

If that boundary is crossed, the visible failure is this: the controller makes locally feasible moves that paint it into a corner later.

Recognize it in a new problem: Look for repeated short-horizon optimization in a feedback loop.
