Action / Control Input

The choice the controller is allowed to make at a particular moment.

01 · the ordinary pressure

Why this idea has to exist

A planner needs to know which knobs it can turn: thrust, steering, torque, investment, braking, or a robot joint command.

A common wrong first move is: Treat every desired change as directly selectable. It fails when a robot cannot choose its next position directly if motors only supply torques under limits.

02 · the object

What the math keeps track of

The working object is a control input, action, or policy output. Use it when you need to separate what you want the system to do from what command you can actually issue.

What the object does: Choose the input and feed it through the system dynamics.

03 · read it with your hands

What to inspect first

Before naming the method, point to a control input, action, or policy output in the setup. Ask what a person could measure, command, update, price, or forbid in one small run.

Now apply one command or one update. Choose the input and feed it through the system dynamics. After that operation, ask what changed in the next state, the path, the value, the constraint set, the policy, or the learned model. If nothing concrete changes, the explanation is still only a label.

The world check is the example: A drone can command rotor thrust, not instant position; the position changes only through acceleration and velocity. Try the same question on another car, drone, rover, robot arm, or reward signal. The concept should still name what changes, what is paid for, and what can fail.

04 · one concrete run

Work it through before naming the formula

A drone pilot may want the drone to be two meters higher, but height is not the command. Suppose the drone is at h = 10 meters, moving upward at v = 0.2 m/s, and the controller raises average rotor thrust from hover thrust to 48 percent above hover for the next dt = 0.1 seconds. In this simple model, that command gives upward acceleration a(u)=4.8 m/s^2. Acceleration changes velocity first: v_next = 0.2 + 0.1*4.8 = 0.68 m/s. Then velocity changes height: h_next = 10 + 0.1*0.68 = 10.068 meters. The drone did not jump to 12 meters. It moved 6.8 centimeters because the action was a motor command applied for one tenth of a second. If the plan writes 'go to 12 meters' as the action, it has skipped the actuator and asked the optimizer for an outcome the drone cannot directly issue. The next action may again increase thrust, but each command still passes through the motors, acceleration, velocity, and only then position.

the actual math, one level deeper

The action u is the command passed into the dynamics. A simple vertical model might use a(u)=10*u, where u is thrust above hover written as a fraction, capped by -0.3 <= u <= 0.5. For u = 0.48, a(u)=4.8 m/s^2 and the updates are v_next = v + dt * a(u) and h_next = h + dt * v_next. With dt = 0.1, v=0.2, and h=10, the result is v_next=0.68 and h_next=10.068. If the optimizer asks for u = 0.9, the actuator limit clips it to u = 0.5, so the model should compute with a=5.0 m/s^2, not pretend the drone can use 90 percent above hover. The next state is produced by x_next = f(x, u), so action limits are limits on u, not on wishes about x_next. A desired height can appear in the cost, for example (h_next - 12)^2, but it is not the control input. The boundary is actuator truth: delay, saturation, dead zones, and rate limits belong in the action model because they decide what command the system can actually obey.

05 · boundary

Where the idea stops working

The action set must reflect actuator limits and legal moves.

When that condition fails, look for this visible break: the plan asks for a move no actuator can produce.

Recognize it in a new problem: Separate what you want the system to do from what command you can actually issue.
