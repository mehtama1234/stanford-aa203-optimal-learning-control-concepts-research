Recursive Feasibility

The property that after applying today's MPC action, tomorrow's optimization problem is still feasible.

01 · the ordinary pressure

Why this idea has to exist

Replanning is only useful if today's legal move does not leave the controller with no legal move next time.

The tempting shortcut is simple: Check only that the current MPC problem has a solution. But that shortcut breaks because the first action of a feasible plan can lead to a state where the next problem is infeasible.

02 · the object

What the math keeps track of

The controller keeps track of a recursively feasible set or terminal condition. This answers a practical question: ask whether solving now preserves the ability to solve later.

The operation is concrete: Design the MPC problem so feasibility propagates from one solve to the next.

03 · one concrete run

Work it through before naming the formula

A car can choose a legal steering command that fits through a narrow gap now but leaves no legal braking option one second later. Recursive feasibility rejects that move because today's feasible plan must hand tomorrow another feasible problem.

the actual math, one level deeper

If x_k is feasible and the MPC applies u_k, recursive feasibility requires the resulting x_{k+1} to remain inside a set from which a feasible horizon plan exists.

04 · boundary

Where the idea stops working

The guarantee depends on model accuracy, constraints, and terminal set design.

If that boundary is crossed, the visible failure is this: the controller works for a few replans and then hits an infeasible optimization.

Recognize it in a new problem: Ask whether solving now preserves the ability to solve later.
