Stochastic Dynamic Programming

Dynamic programming when the next state is uncertain and future value must be averaged over possible outcomes.

01 · the ordinary pressure

Why this idea has to exist

A controller often does not know exactly what will happen after an action because noise, disturbances, or environment changes intervene.

A common wrong first move is: Plan for the most likely next state only. It fails when rare but costly outcomes can dominate safety and expected cost.

02 · the object

What the math keeps track of

The working object is an expected-value bellman equation. Use it when the same action can lead to several next states.

What the object does: Add immediate cost to the expectation of next-state value under the transition distribution.

03 · read it with your hands

What to inspect first

Before naming the method, point to an expected-value bellman equation in the setup. Ask what a person could measure, command, update, price, or forbid in one small run.

Now apply one command or one update. Add immediate cost to the expectation of next-state value under the transition distribution. After that operation, ask what changed in the next state, the path, the value, the constraint set, the policy, or the learned model. If nothing concrete changes, the explanation is still only a label.

The world check is the example: A delivery robot crossing a wet floor must account for possible slip, not only the nominal wheel motion. Try the same question on another car, drone, rover, robot arm, or reward signal. The concept should still name what changes, what is paid for, and what can fail.

04 · one concrete run

Work it through before naming the formula

A delivery rover can cross gravel or detour around it. Crossing gravel costs 1 minute now. Nature then draws a disturbance W. With probability 0.6, W = straight and the rover reaches a state with future value 5. With probability 0.3, W = slip-left and the future value is 12. With probability 0.1, W = slip-right and the future value is 20. These probabilities must add to 1.0 because they describe the full set of next outcomes for this action. The next state is not one promise. The expected future value is 0.6*5 + 0.3*12 + 0.1*20 = 8.6, so the gravel action costs 1 + 8.6 = 9.6. The detour costs 4 minutes now. It has probability 0.9 of reaching a state with value 4 and probability 0.1 of meeting a slow gate with value 9, so its total is 4 + 0.9*4 + 0.1*9 = 8.5. The detour wins even though its immediate cost is larger. If slip-right is serious but not enormous, say value 60, gravel costs 1 + 0.6*5 + 0.3*12 + 0.1*60 = 13.6. If slip-right means a broken axle with repair cost 200, the gravel expected total becomes 1 + 0.6*5 + 0.3*12 + 0.1*200 = 27.6. Now suppose an old dry-floor table claimed P(straight)=0.68, P(slip-left)=0.30, and P(slip-right)=0.02. That would score gravel as 1 + 0.68*5 + 0.30*12 + 0.02*20 = 8.4, just beating the 8.5 detour. After rain, the rover records 50 gravel crossings: 24 straight, 18 slip-left, and 8 slip-right. The measured probabilities are 24/50 = 0.48, 18/50 = 0.36, and 8/50 = 0.16. The same Bellman backup now gives 1 + 0.48*5 + 0.36*12 + 0.16*20 = 10.92, so the detour wins again. The choice changed because rain changed the probabilities, not because detour became cheaper. This is also a state problem. If the table keeps one state called gravel and hides the weather flag, it may combine 100 dry crossings with 50 wet crossings. The blended counts are 92 straight, 48 slip-left, and 10 slip-right out of 150, so P_mix(slip-right)=10/150=0.0667. The mixed backup is 1 + (92/150)*5 + (48/150)*12 + (10/150)*20 = 9.24. That one blended number is wrong for both jobs: it would reject dry gravel even though dry gravel scored 8.4, and it still understates the wet risk compared with 10.92. A good state label separates facts that change tomorrow's draw; a bad label averages unlike situations and makes the expectation look precise while pointing at the wrong world. Stochastic dynamic programming is the same backward reasoning as ordinary dynamic programming, except each possible next state carries probability weight before the action is compared.

the actual math, one level deeper

The stochastic Bellman update uses an expectation over the disturbance or next state: V(x) = min_u [cost(x,u) + E_W V(f(x,u,W))]. For a discrete next-state model, that expectation becomes cost(x,u) + sum over x_next of P(x_next|x,u) V(x_next). The probabilities are part of the dynamics model, not decoration after the fact. In the gravel example, P(straight|x,gravel)=0.6, P(slip-left|x,gravel)=0.3, and P(slip-right|x,gravel)=0.1, so P(straight|x,gravel)+P(slip-left|x,gravel)+P(slip-right|x,gravel)=1.0. The rare slip-right branch still adds 0.1*20 = 2 to the expected future value; with value 60 it adds 0.1*60 = 6; and in the broken-axle version it adds 0.1*200 = 20. The dry-floor model shows how fragile the action choice can be: Q_dry(x,gravel)=1+0.68*5+0.30*12+0.02*20=8.4, while Q(x,detour)=8.5. The measured wet-floor model gives P_hat(straight)=24/50=0.48, P_hat(slip-left)=18/50=0.36, and P_hat(slip-right)=8/50=0.16, so Q_wet(x,gravel)=1+0.48*5+0.36*12+0.16*20=10.92. The Bellman equation did not change; the transition model changed. If wet gravel and dry gravel share one state label, the stored probability is averaging two different worlds and the controller will be wrong on at least one of them. The Markov assumption says P(W_k|X_k,U_k) may depend on the current state and chosen action, but not on X_{k-1}, X_{k-2}, or an old hidden story. The right repair is not to remember every old day; it is to put the needed fact into the present state, for example x = (location=gravel, weather=wet). Then wet and dry get separate transition rows. Costs can also be random. If the slip-left branch adds a 3 minute recovery and the slip-right branch adds a 7 minute recovery, the gravel backup is 0.6*(1+5) + 0.3*(1+3+12) + 0.1*(1+7+20) = 11.2. The branch costs are averaged with the branch futures because both are unknown until W is drawn. A policy that ignores that branch is not optimistic in a harmless way; it has priced a different world than the rover will face. The boundary is risk preference and model truth: expectation is the average cost criterion, so it may still accept rare catastrophic outcomes unless the cost, constraint, or risk measure makes them large enough, and it can only average the probabilities it was given. With slip-right value 60, expectation ranks gravel at 13.6 minutes; a safety rule such as P(broken_axle) <= 0 would reject gravel regardless of its average. If one slip destroys the rover, average minutes may be the wrong measuring stick; the model needs a hard safety constraint or a risk measure, not only a mean.

05 · boundary

Where the idea stops working

The uncertainty model must describe the relevant randomness.

When that condition fails, look for this visible break: the policy is brittle because it ignores low-probability dangerous states.

Recognize it in a new problem: Use it when the same action can lead to several next states.
