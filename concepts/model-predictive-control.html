Model Predictive Control

Repeatedly solve a finite-horizon control problem, apply the first action, observe the new state, and solve again.

01 · the ordinary pressure

Why this idea has to exist

A controller needs future planning but cannot perfectly trust a long open-loop plan.

A common wrong first move is: Compute the whole plan once and execute it blindly. It fails when disturbances and model errors make the real state drift from the planned trajectory.

02 · the object

What the math keeps track of

The working object is a receding-horizon optimization problem. Use it when you need to look for repeated short-horizon optimization in a feedback loop.

What the object does: Optimize over a horizon, apply the first control, shift the horizon, and replan.

03 · read it with your hands

What to inspect first

Before naming the method, point to a receding-horizon optimization problem in the setup. Ask what a person could measure, command, update, price, or forbid in one small run.

Now apply one command or one update. Optimize over a horizon, apply the first control, shift the horizon, and replan. After that operation, ask what changed in the next state, the path, the value, the constraint set, the policy, or the learned model. If nothing concrete changes, the explanation is still only a label.

The world check is the example: An autonomous car plans a few seconds ahead, drives the first fraction, then replans after seeing traffic move. Try the same question on another car, drone, rover, robot arm, or reward signal. The concept should still name what changes, what is paid for, and what can fail.

04 · one concrete run

Work it through before naming the formula

A warehouse cart is 3.0 meters from a loading mark and is moving at 1.0 m/s. Every 0.5 seconds it solves a small plan with three future acceleration commands. At 10:00:00 the optimizer predicts this sequence: brake at -0.8 m/s^2, then -0.6, then -0.2. It also predicts positions 3.45 meters, 3.75 meters, and 3.95 meters from the start of the aisle while staying below the 4.0 meter stop line. MPC applies only the first command, -0.8 m/s^2, for the next 0.5 seconds. A floor bump slows the cart more than expected, so the measured state at 10:00:00.5 is position 3.40 meters and velocity 0.50 m/s, not the predicted 3.45 meters and 0.60 m/s. The controller now discards the old second and third commands as promises made from the wrong state. It solves again from the measured state, with a shifted horizon that now covers 10:00:00.5 to 10:00:02.0. The method is not 'plan once carefully.' It is 'plan, use the first piece, measure, and make a new plan from reality.'

the actual math, one level deeper

At time k, MPC solves a finite-horizon problem for variables u_0...u_{N-1} and predicted states x_0...x_N with x_0 = x_measured(k). The optimization minimizes predicted cost while enforcing dynamics, input bounds, state bounds, and any terminal rule. The implemented policy is pi_MPC(x_measured(k)) = u_0^*, the first control from that solve. After applying u_0^*, the real system produces x_measured(k+1). The next problem is not anchored at the old prediction x_1^pred if the sensor says otherwise; it uses x_0 = x_measured(k+1). This is why MPC is closed loop even though each solve is an open-loop optimization. The boundary is speed and future protection: if the solver is too slow, or the horizon and terminal structure allow a first move that leaves no feasible continuation, the loop can make a legal-looking move now and fail one step later.

05 · boundary

Where the idea stops working

The optimizer must solve fast enough and the horizon/terminal conditions must protect future feasibility.

When that condition fails, look for this visible break: the controller makes locally feasible moves that paint it into a corner later.

Recognize it in a new problem: Look for repeated short-horizon optimization in a feedback loop.
